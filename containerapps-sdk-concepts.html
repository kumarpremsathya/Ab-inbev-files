Composition vs Inheritance and Azure Container Apps SDK

Simple reference for future use in the request-handler project.

Python OOP Azure SDK Container Apps

Quick Takeaway (Main Concept)

This is the exact idea: the main SDK client has operation groups as attributes. You use those attributes to call methods.

# Composition (has-a): main client HAS operation groups
class ContainerAppsAPIClient:
    def __init__(self, credential, subscription_id):
        self.container_apps = ContainerAppsOperations()      # has-a
        self.jobs = JobsOperations()                         # has-a
        self.vnet_connections = VnetConnectionsOperations()  # has-a


# Not inheritance in your usage:
# class ContainerAppsOperations(ContainerAppsAPIClient):
#     pass


client = ContainerAppsAPIClient(credential=cred, subscription_id=sub_id)

# Access composed object, then call method
client.container_apps.get("rg", "app-name")
client.container_apps.begin_create_or_update("rg", "app-name", payload)
client.jobs.list_by_resource_group("rg")

Meaning: ContainerAppsAPIClient is the top-level object, and container_apps/jobs are sub-objects attached to it.

1) Core OOP Concepts

Composition (has-a)

A class keeps another class object as one of its fields/attributes.

class EngineOperations:
    def start(self):
        print("Engine started")

class Car:
    def __init__(self):
        self.engine = EngineOperations()  # has-a relationship

car = Car()
car.engine.start()

Inheritance (is-a)

A class extends another class.

class Vehicle:
    def move(self):
        print("Moving")

class SportsCar(Vehicle):  # is-a relationship
    pass

s = SportsCar()
s.move()

Key point: The SDK usage discussed here is composition, not inheritance.

2) How ContainerAppsAPIClient Uses Composition

The main client object exposes operation groups as attributes:

  • container_apps
  • container_apps_revisions
  • jobs
  • managed_environments
from azure.identity import DefaultAzureCredential
from azure.mgmt.appcontainers import ContainerAppsAPIClient

sub_id = "00000000-0000-0000-0000-000000000000"
client = ContainerAppsAPIClient(
    credential=DefaultAzureCredential(),
    subscription_id=sub_id
)

# Composition access: client HAS these operation groups
app = client.container_apps.get("my-rg", "my-app")
revisions = client.container_apps_revisions.list_revisions("my-rg", "my-app")
jobs = client.jobs.list_by_resource_group("my-rg")
Flow:
  1. Create credential object
  2. Create SDK client with credential + subscription id
  3. Access operation-group attribute (for example client.container_apps)
  4. Call method on operation-group (for example get or begin_create_or_update)

3) Public Cloud vs China Cloud Client Setup

Public cloud usually needs only credential + subscription id. China cloud typically adds authority and endpoint details.

from azure.identity import DefaultAzureCredential, AzureAuthorityHosts
from azure.mgmt.appcontainers import ContainerAppsAPIClient
from msrestazure.azure_cloud import AZURE_CHINA_CLOUD as CHINA

# Public cloud
public_client = ContainerAppsAPIClient(
    credential=DefaultAzureCredential(),
    subscription_id="sub-id"
)

# China cloud
endpoint = CHINA.endpoints.resource_manager
china_client = ContainerAppsAPIClient(
    credential=DefaultAzureCredential(authority=AzureAuthorityHosts.AZURE_CHINA),
    subscription_id="sub-id",
    base_url=endpoint,
    credential_scopes=[endpoint + "/.default"]
)

Why base_url and credential_scopes? They align API endpoint and token audience for sovereign cloud environments.

4) What "Authenticated Client" Means

  • You instantiate ContainerAppsAPIClient once with a credential.
  • Each call through that client uses the SDK auth pipeline automatically.
  • Token is fetched and cached by the credential implementation.
# Same authenticated client used for all calls
client.container_apps.get("rg", "app")
client.container_apps.begin_create_or_update("rg", "app", payload)
client.container_apps.begin_delete("rg", "app")
