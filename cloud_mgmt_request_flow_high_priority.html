Cloud Management – Request Flow (SERVICEBUSQUEUE)

End-to-end path of a catalog request in abi_cloud_mgmt, from the HTTP receiver to the Service Bus request_handler topic, and how to test each step separately.

  • Step 1 – Receiver → tblEventMaster
  • Step 2 – Master → tblActivityAzServiceBusQueue + tblEventPendingActivity
  • Step 3 – Pending → publish to Service Bus

Overview

flowchart LR
    A[POST test_request_receiver] --> B[(tblEventMaster - Pending Approval)]
    B -- Step 2: NewActivity.check_db_for_new_activity --> C[(tblActivityAzServiceBusQueue - In-Progress)]
    B -- Step 2 --> D[(tblEventPendingActivity)]
    D -- Step 3: PendingActivity.get_next_pending_activity --> E[Processor.queue_processor]
    C -- rows In-Progress or Retry --> E
    E --> F[[Service Bus topic request_handler]]
    F --> G[abi-mc-az-requesthandler app]
    G -. sets Status Success or Failed .-> C
    E -. no rows left In-Progress or Retry .-> H[(tblEventCompletedActivity)]

Steps 2 and 3 both run through RequestProcessor.process_request(), triggered by the request_processor timer (every 3 min) or manually via test_processor.

Step 1 – Receiver → tblEventMaster

Entry point: test_request_receiver in function_app.py. Result: one row in tblEventMaster with Status = 'Pending Approval' and a RITM created in ServiceNow.

1.3 Each return statement

#WhereWhat is returnedWhat it adds / means
1 Catalog/Azure/ServiceBusQueue/ServiceBusQueue.py
snow_data → return self.request_data		 The same data dict (self.request_data = data is a reference, not a copy) Adds short_description, description, business_service, variables (SNOW form fields) and payload["action"]. Step 2 reads action back from tblEventMaster.Payload.
2 RequestReceiver/ActivityNames/AzActivityNames.py
return self.request_data		 The dict from ① Pure router that picks a catalog class by ActivityName. Stored as activity_type_data in RequestReceiver.
3 ServiceNow/SnowRequest.py
create → return data		 The same dict again Adds SnowId (REQ number), SnowStatusCode, SnowStatus, SnowItemId (RITM number), SnowItemStatusCode, SnowItemStatus. Uploads the data to the RITM as a JSON attachment.
4 RequestReceiver/RequestReceiver.py
event_db_insert → return self.objdb.executescalar(...)		 EventId (int) Comes from OUTPUT inserted.EventId in the MERGE. DB.executescalar with action="eventinsert" returns fetchone()[0] and commits. In the Request path it is only used by the commented-out email.
5 request_initilize → return self.data["SnowItemId"] RITM number string Final value of Step 1.
6 test_request_receiver → func.HttpResponse(f"Done. SnowItemId: {snow_tkt}") HTTP 200 What you see in Postman.
Key point: (1), (2) and (3) all return one and the same dict object, enriched as it passes through. What gets written to tblEventMaster is the original request plus everything each layer added.

sequenceDiagram
    participant T as test_processor (function_app.py)
    participant P as RequestProcessor.process_request

    participant M as DbActivityManager

    participant Z as AzPayloadDeserializer.deserialize
    participant Q as AzServiceBusQueue.activity_data

    participant PA as tblEventPendingActivity

    T->>P: process_request()
    P->>N: check_db_for_new_activity()

    EM-->>M: rows
    M-->>N: (1) return datasets

        N->>SR: snow_get_ritm_status(SnowItemId)
        SR-->>N: (2) return snow_ritm

        alt approved
            N->>Z: deserialize(dataset) when Cloud is Azure
            Z->>Q: activity_data(dataset) when ActivityName is SERVICEBUSQUEUE
            Q->>Q: json.loads(dataset.Payload)
            Q->>AT: MERGE insert, Status In-Progress, RetryAttemptedAt now
            Q->>M: insert_activity_pending(dataset)
            M->>PA: MERGE insert EventId, ActivityName, RetryAttemptedAt now
            Q-->>Z: (3) return None
            Z-->>N: (4) return None

            M->>EM: UPDATE Status In-Progress

            M->>EM: UPDATE Status
        else still waiting for approval
            Note over N: status is None, row picked again next run
        end
    end
    N-->>P: (5) return None
    P-->>T: return
    T-->>T: (6) HTTP 200 Done

3.2 Call chain (sequence diagram)

sequenceDiagram
    participant T as test_processor (function_app.py)
    participant PE as PendingActivity.get_next_pending_activity
    participant M as DbActivityManager
    participant SR as SnowRequest.snow_get_ritm_status
    participant AZ as AzProcessor.initialize
    participant PR as Processor.queue_processor
    participant SB as ServiceBus topic request_handler
    participant DB as SQL tables

    T->>PE: process_request() then get_next_pending_activity()
    PE->>M: get_pending_activity()
    M->>DB: SELECT tblEventPendingActivity JOIN tblEventMaster WHERE RetryAttemptedAt older than now
    M-->>PE: (1) return datasets
    loop each dataset with ActivityType Request
        PE->>SR: snow_get_ritm_status(SnowItemId)
        SR-->>PE: (2) return snow_ritm
        PE->>PE: (3) determine_request_status returns status or None
        alt status is not None
            PE->>M: IncompleteActivity - Aborted and insert_activity_completed
        else status is None
            PE->>AZ: initialize_handler(dataset) when Cloud is Azure
            AZ->>AZ: (4) get_table_and_topic_names returns TABLE_NAME
            AZ->>PR: queue_processor(tblname, dataset)
            PR->>M: get_activity_info(tblname, EventId)
            M-->>PR: (5) return rows In-Progress or Retry
            loop each row
                PR->>PR: payload = row columns + ActivityName + TableName, pop RetryAttemptedAt
                PR->>PR: (6) generate_unique_key returns sha256 of payload
                opt row RetryAttemptedAt older than now
                    PR->>SB: publish_api - send_messages (commented in dry run)
                end
            end
            alt pending rows greater than 0
                PR->>M: get_pending_next_retry_time
                M-->>PR: (7) return earliest row
                PR->>M: update_activity_pending_retry
            else no rows left
                PR->>M: get_activity_info_failed_count
                M-->>PR: (8) return SuccessCount and FailedCount
                PR->>M: insert_activity_completed Success or Failed
            end
        end
    end
    PE-->>T: return None, HTTP 200 Done

3.3 Each return statement

#WhereWhat is returnedWhat it means
1DbActivityManager.get_pending_activityRows with EventId, ActivityName, ActivityType, SnowId, SnowItemId, SnowItemStatusCode, SnowItemStatus, CloudOnly pending rows whose RetryAttemptedAt is in the past. No Payload here – the payload comes from the activity table.
2snow_get_ritm_statusSNOW dict or emptyEmpty → skipped. No bypass in this file unless you add one.
3determine_request_status'Closed Incomplete' / 'Cancelled' / 'Closed Complete' / NoneNon-None → activity is aborted. None → continue to publish.
4AzProcessor.get_table_and_topic_names'tblActivityAzServiceBusQueue'Unknown name → ValueError (caught in get_next_pending_activity, email sent, exception logged in tblActivityInfo).
5get_activity_infoActivity rows with Status In-Progress or RetryEach row becomes one Service Bus message.
6ServiceBusClientAbstract.generate_unique_keySHA-256 hex of the payloadUsed as message_id. Same row → same id on every run, so Service Bus duplicate detection (if enabled on the topic) drops repeats.
7get_pending_next_retry_timeEarliest In-Progress/Retry rowIts RetryAttemptedAt is copied to tblEventPendingActivity.
8get_activity_info_failed_countTotalRecords, SuccessCount, FailedCount0 failed → Success; mixed → Failed / Implemented Partially; 0 success → Failed.
