1. The big picture

  1. We create a resource group and a Service Bus namespace inside it (the queue will live in the namespace).
  2. We create an app registration. This creates an identity (a service principal) with a client ID and a client secret.
  3. On the resource group we give that service principal the Contributor role (role assignment).
  4. The test script logs in as that service principal (tenant ID + client ID + secret) and creates, updates and deletes a queue in the namespace.
Yes: the service principal is created in App registrations, it is given Contributor on the resource group that holds the Service Bus namespace, and its credentials are used in the script to manage the queue.
ConceptQuestionWhere you set it up
AuthenticationWho are you?App registration → service principal + client secret
AuthorizationWhat may you do?Resource group → Access control (IAM) → role assignment

A newly created service principal can sign in but can do nothing until it is given a role.

3. Portal setup, step by step

Do this in the personal Azure account (use an InPrivate window so the org session is not reused).

  1. Resource group – create one, e.g. prem-servicebus. Everything goes here, so cleanup is a single delete.
  2. Service Bus namespace – create it inside that group, e.g. mit-servicebus. Basic SKU is enough for queues.
  3. App registration – Microsoft Entra ID → App registrations → New registration. Name it (e.g. sbq-test-sp), single tenant, no redirect URI → Register.
    On the Overview page note the Application (client) ID and the Directory (tenant) ID.
  4. Client secret – the app → Certificates & secrets → New client secret. Copy the Value immediately (it is hidden afterwards). Do not copy the "Secret ID".
  5. Role assignment – open the resource group (not the app) → Access control (IAM) → Add → Add role assignment:
    • Role tab: Contributor is not under "Job function roles". Open the Privileged administrator roles tab (or search "Contributor"), select Contributor, click Next.
    • Members tab: choose User, group, or service principal → Select members → search for your app name (e.g. sbq-test-sp) → Select.
    • Review + assign (click it twice).
    Verify: IAM → Role assignments → the app is listed with Contributor. Wait 1–2 minutes for it to take effect.
  6. Collect the four values for the script:
    ValueWhere to find it
    Tenant IDApp registration → Overview (Directory ID)
    Client IDApp registration → Overview (Application ID)
    Client secretThe Value copied in step 4
    Subscription IDSubscriptions → your subscription → Overview
No Key Vault and no az login are needed. The script receives the credentials directly.

4. Why Contributor (and not the Service Bus roles)

RolePlaneCan it create / update / delete a queue?
Contributor (on the resource group)ManagementYes
Azure Service Bus Data OwnerDataNo – gives 403 on the management call
Azure Service Bus Data SenderDataNo (send messages only)
Azure Service Bus Data ReceiverDataNo (receive messages only)

The handler uses ServiceBusManagementClient (Azure Resource Manager), so it needs a management-plane role. The Data roles are only for sending and receiving messages. Contributor on the group is inherited by the namespace and every queue inside it.

  1. ClientSecretCredential sends tenant ID, client ID and secret to Entra ID and gets an access token (a 200 on /oauth2/v2.0/token in the log).
  2. The handler calls queues.get to see whether the queue exists (404 means it does not).
  3. For Create / Update it calls queues.create_or_update (one PUT call for both). For Delete it calls queues.delete.
  4. Azure checks the token and the role assignment, then performs the change. Without the role you get 403.

6. The test script

File: test_servicebus_queue_personal.py in the project root. Secrets are shown as placeholders here. The file is excluded from git on your machine via .git/info/exclude.

import json, logging, os, sys
from azure.identity import ClientSecretCredential
from azure.mgmt.servicebus import ServiceBusManagementClient

TENANT_ID = "<tenant-id>"
CLIENT_ID = "<client-id>"
CLIENT_SECRET = "<client-secret-value>"
SUBSCRIPTION_ID = "<personal-subscription-id>"
RESOURCE_GROUP = "<resource-group>"
NAMESPACE = "<namespace-name>"
QUEUE_NAME = "test-queue"

# The handler only changes Azure when its environment check matches
os.environ["Environment"] = "local"
logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

from Catalog.Azure.ServiceBusQueueMgmt.servicebus_queue_mgmt import AzServiceBusQueueMgmt

subscription_id, resource_group, namespace, queue_name = SUBSCRIPTION_ID, RESOURCE_GROUP, NAMESPACE, QUEUE_NAME
if len(sys.argv) >= 4:
    subscription_id, resource_group, namespace = sys.argv[1:4]
    queue_name = sys.argv[4] if len(sys.argv) > 4 else QUEUE_NAME
if any(v.startswith("<") for v in (subscription_id, resource_group, namespace)):
    sys.exit("Fill in SUBSCRIPTION_ID, RESOURCE_GROUP and NAMESPACE at the top of the script.")

credential = ClientSecretCredential(tenant_id=TENANT_ID, client_id=CLIENT_ID, client_secret=CLIENT_SECRET)
client = ServiceBusManagementClient(credential, subscription_id)


def run(action, properties=None):
    payload = {
        "ActivityId": "TEST-ACTIVITY", "EventId": "TEST-EVENT",
        "SubscriptionId": subscription_id, "ResourceGroupName": resource_group,
        "NamespaceName": namespace, "QueueName": queue_name,
        "Action": action, "Zone": "GHQ",
        "QueueProperties": json.dumps(properties) if properties else None,
    }
    handler = AzServiceBusQueueMgmt(payload)
    handler._client = client          # skips the Key Vault based credential lookup
    result = handler.manage_queue()
    print(f"\n[{action}] result: {result}")
    return result


def show():
    q = client.queues.get(resource_group, namespace, queue_name)
    print(f"ttl={q.default_message_time_to_live} "
          f"max_size_mb={q.max_size_in_megabytes} max_delivery_count={q.max_delivery_count}")


run("Create", {"default_message_time_to_live": "P14D", "lock_duration": "PT5M"})
show()

run("Update", {"lock_duration": "PT1M"})
show()   # lock_duration changes; ttl and max size stay as created

run("Delete")
try:
    client.queues.get(resource_group, namespace, queue_name)
    print("FAIL: queue still exists")
except Exception as e:
    print(f"  confirmed deleted ({type(e).__name__})")

What the parts do

  • The six constants are the values from the portal setup (section 3).
  • ClientSecretCredential is the service principal login (tenant + client ID + secret).
  • ServiceBusManagementClient is the client that talks to Azure Resource Manager using that login.
  • handler._client = client gives the real handler this ready-made client, so it does not look up the org credentials in Key Vault. Create / update / delete logic is the real handler code.
  • run() builds a payload like the real request and calls manage_queue(); show() prints the queue's current settings.

7. How to run the script

  1. Complete the portal setup (section 3) and confirm Contributor is listed under the resource group's Role assignments. Wait 1–2 minutes.
  2. Open the script and fill in the six constants (tenant ID, client ID, client secret Value, subscription ID, resource group, namespace).
  3. Make sure the Create, Update and Delete lines are all uncommented (while debugging some may be commented out).
  4. Open a terminal in the project folder, activate the venv and run: 
    cd C:\Users\C901925\Desktop\abi-mc-az-requesthandler
.\.venv\Scripts\Activate.ps1
python .\test_servicebus_queue_personal.py
    Or without activating: .\.venv\Scripts\python.exe test_servicebus_queue_personal.py. Optionally pass values instead of editing the file: python test_servicebus_queue_personal.py <subscription_id> <resource_group> <namespace> [queue_name].
  5. Watch the console, and refresh Namespace → Queues in the portal after each step.

Expected result

If the result is just True and nothing changes in Azure, the handler's environment check did not match os.environ["Environment"] and it only logged "[NON-PROD] Would ...". Make the two values match.

8. ClientSecretCredential vs. DefaultAzureCredential

ClientSecretCredential logs in as one specific identity that you name. You give it the tenant ID, client ID and secret, and it asks Entra ID for a token as that service principal. It always does exactly that, so it is predictable.

DefaultAzureCredential is not a login method itself. It tries a list of methods in order and uses the first one that works:

  1. Environment variables (AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_CLIENT_SECRET)
  2. Workload identity
  3. Managed identity (when running in Azure)
  4. Visual Studio Code or Visual Studio sign-in
  5. Azure CLI (az login)
  6. Azure PowerShell / azd

The same code then works on a laptop (using your az login) and in Azure (using a managed identity), with no secret in the code.

ClientSecretCredentialDefaultAzureCredential
Identity usedAlways the service principal you pass inWhichever method succeeds first
Needs a secret in code or configYesNo (uses the environment, CLI or managed identity)
PredictableYesLess so, it can pick up an unexpected identity
Best forFixed service principal, as in the test scriptCode that runs in several places

In this repo

  • DefaultAzureCredential reads the Key Vault secret from KEYVAULT_URI. The function app uses its own managed identity (or your az login locally) for that.
  • That secret holds the service principal's client_id, secret and tenant.
  • ClientSecretCredential then uses those values to log in as the org service principal and manage the Azure resources.

So the first credential is used to get to the secret, and the second does the actual work.

In the test script

  • It uses ClientSecretCredential directly with the personal service principal.
  • That skips the Key Vault step, so no az login is needed (it was blocked on the laptop).
  • It also guarantees the calls run as the service principal that has Contributor, not as some other identity.

9. How get_servicebus_client authenticates (full flow)

ServicebusClient().get_servicebus_client(self.subscription_id, self.cloud) works in two phases, and two different identities are involved:

  • Phase A (when the client is built): the Function App's own identity reads the org service principal's credentials from Key Vault.
  • Phase B (on the first queue call): that service principal gets a token and calls Azure Resource Manager.

Where your test script fits

It sets handler._client = client directly, so the self.client property never calls get_servicebus_client. Steps 2–9 are skipped: no Key Vault and no DefaultAzureCredential. Steps 10–11 run the same way, using your personal service principal.

Two things to note

  • truststore at the top of the handler: servicebus_queue_mgmt.py now starts with import truststore; truststore.inject_into_ssl(). That is only for the proxy on your laptop. Move it into the test script before merging, because truststore probably isn't in requirements.txt, so the deployed function would fail to import it.
  • China cloud login (worth confirming): for China, ClientSecretCredential is created without an authority, so it signs in through the global login.microsoftonline.com. A China tenant normally needs login.chinacloudapi.cn. This is the existing shared pattern, not something changed here, so it's worth checking whether China requests work today.

12. Cleanup and security

The client secret was pasted into a chat and hard-coded in the script. Treat it as exposed.
  1. Delete the resource group (removes the namespace, queues and the role assignment): Portal → Resource groups → Delete.
  2. Delete the client secret or the whole app registration: App registrations → your app → Certificates & secrets (or Delete).
  3. Delete the script or blank out the constants. Never commit it.
  4. Before merging the handler, switch its environment check back to "production".
