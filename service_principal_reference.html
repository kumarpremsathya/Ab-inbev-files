Service Principal (SPN) — Reference Guide

What it is · How it authenticates · Where it is used · Why it matters

What is a Service Principal?

A Service Principal is like a user account for an application — instead of a human logging in, your code uses it to authenticate and access Azure resources automatically.

Just as a human needs a username + password to log into Azure Portal, an application needs a client_id + client_secret + tenant_id to authenticate programmatically.

The 3 Key Properties

PropertyHuman EquivalentPurpose
client_idUsernameIdentifies which application is authenticating
client_secretPasswordProves the identity of the application
tenant_idDomain / OrganisationIdentifies which Azure AD directory to authenticate against

This is exactly what is stored in Azure Key Vault as a JSON string:

{
  "client_id": "abc123-...",
  "secret":    "xyz789-...",
  "tenant":    "tenant-id-..."
}

Human Account vs Service Principal

❌ Human Account (not suitable for automation)

  • Requires MFA — blocks automation
  • Password expires — breaks scheduled jobs
  • Tied to a person — if they leave, access breaks
  • Cannot run unattended at 6 AM
  • Audit logs mixed with human activity

✅ Service Principal (designed for automation)

  • No MFA — fully automated
  • Controlled expiry — managed by team
  • Tied to application — independent of people
  • Runs unattended on any schedule
  • Clean audit trail per application

How Authentication Works — Step by Step

1
Code wants to query Azure Resource Graph
↓
2
Azure asks: "Who are you?"
↓
3
Code presents: client_id + client_secret + tenant_id (fetched from Key Vault)
↓
4
Azure AD verifies credentials → issues an OAuth2 access token
↓
5
Code uses that token to call the Azure Resource Graph API
↓
6
Azure checks RBAC: "Does this SPN have permission to read resources?"
↓
7
✅ If yes → returns SQL Server / Database data

In code — shared_code/resourcegraph_client.py:

credentials = ClientSecretCredential(
    client_id     = spn_token["client_id"],    # identifies the app
    client_secret = spn_token["secret"],       # proves identity
    tenant_id     = spn_token["tenant"]        # which Azure AD org
)
# Azure SDK handles OAuth token exchange internally ↑
res_graph_client = ResourceGraphClient(credentials)
# client is now authenticated and ready to query Azure

Two SPNs Used in This Project

Secret Name in Key VaultUsed ForCloud
az-public-spn-reader Read Azure Public resources (SQL servers, databases, etc.) AzurePublicCloud
az-china-spn-reader Read Azure China resources AzureChinaCloud
Why two separate SPNs?
Azure China is a completely separate Azure instance operated by 21Vianet — it has its own Azure AD, its own endpoints, and requires its own SPN registered specifically in the China tenant.

Two Layers of SPN Authentication in This Project

Layer 1 — Access Key Vault
AZURE_CLIENT_ID + AZURE_CLIENT_SECRET + AZURE_TENANT_ID stored in local.settings.json
→ Used by DefaultAzureCredential in akv_secrets.py to authenticate to Key Vault
↓ unlocks ↓
Layer 2 — Query Azure Resource Graph
az-public-spn-reader / az-china-spn-reader — stored inside Key Vault
→ Used by ClientSecretCredential in resourcegraph_client.py to authenticate to Azure Resource Graph

Why this layered approach?

The real query credentials (Layer 2) are never stored in code or config files. They live only in Key Vault and are fetched securely at runtime. Even if someone reads your source code or local.settings.json, they cannot access the Resource Graph — they would also need access to the Key Vault.

local.settings.json → AZURE_CLIENT_ID + SECRET + TENANT
    └── DefaultAzureCredential → authenticates to Azure Key Vault
          └── Key Vault returns SPN #2 credentials (JSON string)
                └── json.loads() → dict {client_id, secret, tenant}
                      └── ClientSecretCredential → authenticates to Azure Resource Graph
                              └── returns SQL Server / Database data ✅

Summary

  • A Service Principal = application identity in Azure AD (like a user account for code)
  • Has 3 properties: client_id, client_secret, tenant_id
  • Azure AD verifies these → issues an OAuth2 token → token is used for all API calls
  • Stored in Azure Key Vault as a JSON string — never hardcoded in code
  • json.loads() converts the Key Vault string into a Python dict at runtime
  • This project uses 2 layers: one SPN to open Key Vault, another inside Key Vault to query Azure
  • Separate SPNs exist for Public Cloud and China Cloud
